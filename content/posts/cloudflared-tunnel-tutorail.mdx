## Por que você deveria se importar com isso?

Sabe aquela aplicação que roda na sua máquina e você quer mostrar para o mundo? Ou aquele sistema de monitoramento que precisa ficar acessível de qualquer lugar? O problema é que a maioria dos tutoriais **não** ensina a fazer isso com segurança.

Neste artigo vamos publicar um serviço de forma:

- **Segura**: sem expor portas do servidor diretamente na internet.
- **Simples**: ferramentas gratuitas e poucos arquivos de configuração.
- **Profissional**: com segredos fora do código, imagens fixadas e autenticação na borda.

**Ferramentas**: Docker (empacotamento), Cloudflare Tunnel (caminho seguro até a aplicação) e Prometheus (nosso exemplo prático).

## Parte 1: entendendo o Cloudflare Tunnel

### O problema tradicional

Para publicar um serviço, o caminho clássico é abrir uma porta no firewall/roteador, ter um IP público e encaminhar o tráfego. Isso deixa o servidor exposto a varreduras e ataques diretos.

### A solução: conexão de saída

O Cloudflare Tunnel inverte a lógica: o conector `cloudflared` estabelece conexões **de saída** com a rede da Cloudflare, e as requisições dos usuários chegam por esse canal já aberto. Nenhuma porta de entrada precisa ser liberada<Cite id="cf-tunnel" />.<Sidenote>Por padrão, o cloudflared mantém quatro conexões com pelo menos dois data centers distintos da Cloudflare: a queda de um deles não derruba o serviço.</Sidenote> Compare os dois fluxos — clique em *Reproduzir fluxo*:

**Analogia**: é como ligar para uma central e deixar a linha aberta. Quando alguém quer falar com você, a central transfere a ligação — mas ninguém tem o seu número direto.

<Callout type="info" title="Zero Trust em uma frase">
"Nunca confie, sempre verifique": nenhum acesso é implicitamente confiável por estar na rede certa; cada requisição é autenticada e autorizada<Cite id="nist-800-207" />. O túnel resolve a exposição de rede; a **autenticação** (Parte 4) completa o modelo.
</Callout>

### Vocabulário essencial

- **Túnel**: o canal persistente entre seu ambiente e a Cloudflare, identificado por um <Term def="Universally Unique Identifier: identificador de 128 bits, gerado de forma que a colisão seja praticamente impossível.">UUID</Term>.
- **cloudflared**: o conector (daemon) que cria e mantém o túnel; mantém múltiplas conexões para redundância.
- **Túnel gerenciado remotamente**: a configuração (rotas) fica no painel da Cloudflare; o conector só precisa do **token**.
- **Rede bridge** (Docker): rede virtual privada em que os containers se encontram pelo nome do serviço.
- **Volume**: armazenamento persistente que sobrevive à recriação do container.

## Parte 3: mão na massa

### Estrutura de arquivos

```text
prometheus-stack/
├── .gitignore
├── compose.yaml               # orquestra os containers
├── secrets/
│   └── cloudflare_token.txt   # token do túnel (NUNCA versionar)
└── prometheus/
    ├── prometheus.yml         # configuração do Prometheus
    └── rules/                 # regras de alerta (vazio por enquanto)
```

```bash
mkdir -p ~/prometheus-stack/prometheus/rules ~/prometheus-stack/secrets
cd ~/prometheus-stack
printf 'secrets/\n' > .gitignore
```

### Passo 1: o compose.yaml

O arquivo segue a especificação Compose: `compose.yaml` é o nome preferido e o atributo `version` é obsoleto<Cite id="compose-spec" />.

```yaml title="prometheus-stack/compose.yaml"
networks:
  monitoring:
    driver: bridge

volumes:
  prometheus_data: {}

secrets:
  cloudflare_token:
    file: ./secrets/cloudflare_token.txt

services:
  prometheus:
    image: prom/prometheus:v3.15.0  # versão fixada; atualize via Renovate/Dependabot
    container_name: prometheus
    restart: unless-stopped
    command:
      - "--config.file=/etc/prometheus/prometheus.yml"
      - "--storage.tsdb.path=/prometheus"
      - "--storage.tsdb.retention.time=15d"
    volumes:
      - ./prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - ./prometheus/rules:/etc/prometheus/rules:ro
      - prometheus_data:/prometheus
    ports:
      - "127.0.0.1:9090:9090"  # somente na máquina local
    networks: [monitoring]
    user: "65534:65534"        # nobody
    read_only: true
    tmpfs: [/tmp]
    security_opt: ["no-new-privileges:true"]
    cap_drop: [ALL]

  cloudflared:
    image: cloudflare/cloudflared:2026.10.0
    container_name: cloudflared
    restart: unless-stopped
    command: tunnel --no-autoupdate run
    environment:
      TUNNEL_TOKEN_FILE: /run/secrets/cloudflare_token
    secrets: [cloudflare_token]
    networks: [monitoring]
    read_only: true
    tmpfs: [/tmp]
    security_opt: ["no-new-privileges:true"]
    cap_drop: [ALL]
    depends_on: [prometheus]
```

O que mudou em relação à primeira versão deste artigo — e por quê:

| Antes | Agora | Motivo |
| --- | --- | --- |
| `ports: "9090:9090"` | `"127.0.0.1:9090:9090"` | Sem o IP, o Docker publica em **todas** as interfaces e suas regras de NAT ignoram o UFW<Cite id="docker-firewall" />. |
| `--web.enable-admin-api` e `--web.enable-lifecycle` | removidos | Permitem apagar séries e desligar o servidor via HTTP; jamais devem ficar acessíveis pelo túnel<Cite id="prom-security" />. |
| `--web.console.*` | removidos | Os templates de console deixaram de ser distribuídos a partir do Prometheus 3<Cite id="prom-migration" />. |
| Token no `command` | `TUNNEL_TOKEN_FILE` + *secret* | O token não aparece no `compose.yaml`, no Git nem no `docker inspect`<Cite id="cf-run-parameters,compose-secrets" />. |
| Imagens `:latest` | versões fixadas | Builds reproduzíveis e atualizações deliberadas. |

A primeira linha da tabela é o erro mais comum — e o menos intuitivo: o firewall parece ativo, mas a porta continua aberta. Combine as opções na figura e observe quais caminhos chegam ao serviço<Cite id="docker-firewall" />.

### Passo 2: configurar o Prometheus

```yaml title="prometheus-stack/prometheus/prometheus.yml"
global:
  scrape_interval: 15s
  evaluation_interval: 15s
  external_labels:
    environment: "homelab"

# rule_files:
#   - /etc/prometheus/rules/*.yml

scrape_configs:
  - job_name: "prometheus"
    static_configs:
      - targets: ["localhost:9090"]
```

### Passo 3: validar e subir o Prometheus

```bash
docker compose config --quiet && echo "compose.yaml válido"
docker compose up -d prometheus
docker compose ps
curl -s http://127.0.0.1:9090/-/healthy
```

Saída esperada: `Prometheus Server is Healthy.` — se chegou aqui, o Prometheus está rodando.

<Callout type="tip">
Usuários no grupo `docker` não precisam de `sudo`. Mas lembre: pertencer ao grupo `docker` equivale, na prática, a acesso root no host.
</Callout>

## Parte 4: conectando com a Cloudflare

> As capturas de tela abaixo são de outubro de 2025. O painel da Cloudflare muda com frequência; os nomes de menu podem variar — a documentação oficial é a referência<Cite id="cf-tunnel" />.

1. Acesse o painel da Cloudflare e abra o **Cloudflare One** (antigo Zero Trust).

<Figure src="/images/cloudflare/cloudflare-tunnel/tutorial_01.png" alt="Painel da Cloudflare com o item Zero Trust destacado" />

2. Em **Networks**, abra a seção de **Tunnels** e clique em **Create a tunnel**.

<Figure src="/images/cloudflare/cloudflare-tunnel/tutorial_02.png" alt="Tela de túneis com o botão Create a tunnel" />

3. Selecione o conector **Cloudflared** e dê um nome ao túnel.

<Figure src="/images/cloudflare/cloudflare-tunnel/tutorial_03.png" alt="Seleção do tipo de conector Cloudflared" />

<Figure src="/images/cloudflare/cloudflare-tunnel/tutorial_04.png" alt="Campo para nomear o túnel" />

4. Escolha o ambiente **Docker**. O painel exibirá um comando com `--token eyJ…`. **Copie apenas o token** e grave-o no arquivo de segredo:

<Figure src="/images/cloudflare/cloudflare-tunnel/tutorial_05.png" alt="Instruções de instalação do conector com o token" />

```bash
# O espaço inicial evita que o comando fique no histórico (com HISTCONTROL=ignorespace)
 read -rs TOKEN && printf '%s' "$TOKEN" > secrets/cloudflare_token.txt && unset TOKEN
chmod 700 secrets
chmod 644 secrets/cloudflare_token.txt  # lido pelo usuário não-root do container
```

<Callout type="security" title="Trate o token como uma senha de produção">
Quem tem o token controla o túnel. Se ele vazar (commit no Git, print em grupo, log de CI), **revogue e gere outro imediatamente** no painel. A pasta `secrets/` com permissão `700` impede que outros usuários do host a leiam; o arquivo `644` é necessário porque o container roda como usuário não-root.
</Callout>

5. Suba o conector e verifique os logs:

```bash
docker compose up -d
docker compose logs -f cloudflared   # procure por "Registered tunnel connection"
```

No painel, o túnel deve aparecer como **Healthy/Connected**.

6. Publique a rota (*Published application routes*, antigo *Public Hostname*):

<Figure src="/images/cloudflare/cloudflare-tunnel/tutorial_06.png" alt="Configuração de hostname público com subdomínio e serviço HTTP" />

- **Subdomínio**: `prom`; **Domínio**: o seu.
- **Serviço**: tipo `HTTP`, URL `prometheus:9090`.

Por que `prometheus:9090` e não `localhost:9090`? Dentro do container `cloudflared`, `localhost` é o próprio container. O nome do serviço é resolvido pelo DNS interno da rede `monitoring`.

### Parte 4.1: proteja com Cloudflare Access (obrigatório)

<Callout type="danger" title="O Prometheus não tem autenticação">
Sem uma camada de autenticação, qualquer pessoa com a URL consulta suas métricas — nomes de hosts, versões, topologia — material valioso para um atacante<Cite id="prom-security" />. Crie uma aplicação **self-hosted** no Cloudflare Access para `prom.seudominio.com` e exija login (Google, Microsoft, GitHub ou PIN por e-mail) antes de liberar a rota<Cite id="cf-one" />.
</Callout>

### Parte 4.2: teste fora da rede local

<Figure src="/images/cloudflare/cloudflare-tunnel/tutorial_07.png" alt="Prometheus acessado pelo celular via rede móvel" maxWidth={360} />

Desligue o Wi-Fi do celular, use a rede móvel e acesse `https://prom.seudominio.com`. Se pedir login (Access) e depois mostrar o Prometheus, você publicou um serviço do jeito certo.

## Melhorias para produção

**1. Backup.** O Compose prefixa volumes com o nome do projeto (`prometheus-stack_prometheus_data`). Para uma cópia consistente, pare o container antes do `tar`:

```bash
docker compose stop prometheus
docker run --rm -v prometheus-stack_prometheus_data:/data:ro -v "$PWD/backup":/backup \
  alpine:3.22 tar czf "/backup/prometheus-$(date +%F).tar.gz" -C /data .
docker compose start prometheus
```

**2. Atualizações.** Com versões fixadas, use Renovate ou Dependabot para receber PRs de atualização — e revise as *release notes*.

**3. Borda.** Configure WAF e *rate limiting* na Cloudflare para os hostnames publicados.

**4. Monitore o monitoramento.** Adicione o Alertmanager e alertas para container parado, disco cheio e túnel desconectado (o `cloudflared` expõe métricas com a flag `--metrics`)<Cite id="cf-run-parameters" />.

## Conclusão

Com um túnel de saída, segredos fora do código, containers endurecidos e autenticação na borda, você publica serviços com uma postura de segurança comparável à de ambientes corporativos — sem abrir uma única porta no roteador.
