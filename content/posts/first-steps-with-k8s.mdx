Esta publicação nasceu das minhas anotações aprendendo Kubernetes — o orquestrador de containers que herdou ideias do Borg, o sistema interno do Google<Cite id="borg" />. Antes de avançar, alguns conceitos com uma analogia de condomínio:

- **Pod**: apartamento (os containers moram nele).
- **Node**: prédio (os Pods ficam nele) — geralmente um servidor ou VM.
- **Cluster**: condomínio (conjunto de Nodes coordenados).
- **Deployment**: síndico (garante que tudo funcione; gerencia vários Pods).
- **Service**: portaria (recebe visitas e encaminha, com balanceamento).
- **Ingress / Gateway**: guarita da rua (primeira entrada HTTP, encaminha para o Service).
- **Namespace**: blocos do condomínio (isolamento lógico).

A hierarquia é **Container → Pod → Node → Cluster**. Um Pod pode ter vários containers, mas eles devem ser inseparáveis (compartilham rede e volumes)<Cite id="k8s-pods" />.

<Figure src="/images/k8s/pod.png" alt="Diagrama: containers dentro de um Pod, Pods dentro de um Node" maxWidth={520} />

Pods são **efêmeros**: se morrem, não voltam sozinhos. Por isso usamos um **Deployment**, que mantém o número desejado de réplicas. Como cada Pod recriado ganha um novo IP, o **Service** oferece um endereço estável com balanceamento. E o **Ingress** (ou o **Gateway API**) recebe o tráfego HTTP externo e o roteia ao Service correto.

Os Pods também têm um ciclo de vida bem definido, influenciado pela *restart policy*<Cite id="k8s-pod-lifecycle" />:

<Figure src="/images/k8s/pod_life_cicle.png" alt="Ciclo de vida de um Pod: Pending, Running, Succeeded, Failed e Unknown" />

## Pré-requisitos

- Um cluster Kubernetes (usei **k3s** em um servidor local; minikube, kind ou um serviço gerenciado também servem).
- `kubectl` configurado.

No k3s, o kubeconfig fica em `/etc/rancher/k3s/k3s.yaml`, legível apenas pelo root. Em vez de usar `sudo` em todo comando, copie-o para o seu usuário com permissões restritas<Cite id="k3s-docs" />:

```bash
mkdir -p ~/.kube
sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
sudo chown "$USER": ~/.kube/config
chmod 600 ~/.kube/config
kubectl get nodes
```

## Nível 1: seu primeiro Pod

```yaml title="pod.yaml"
apiVersion: v1          # API "core" (Pod, Service, ConfigMap, Secret)
kind: Pod               # o que estamos criando
metadata:
  name: meu-nginx       # único no namespace
  labels:
    app: nginx          # labels: é assim que Services e Deployments encontram Pods
spec:
  containers:
    - name: nginx
      # Imagem não-root (escuta na 8080). Em produção, fixe a versão mais recente (ou o digest).
      image: nginxinc/nginx-unprivileged:1.28-alpine
      ports:
        - containerPort: 8080   # documentação; não expõe nada para fora
```

```bash
kubectl apply -f pod.yaml                    # cria ou atualiza
kubectl get pods -o wide                     # status, IP e Node
kubectl describe pod meu-nginx               # eventos e motivo de falhas
kubectl port-forward pod/meu-nginx 8080:8080 # túnel temporário → http://localhost:8080
kubectl logs -f meu-nginx                    # logs em tempo real
kubectl exec -it meu-nginx -- sh             # shell no container
kubectl delete -f pod.yaml
```

**Problemas comuns**: `ImagePullBackOff` (nome/tag da imagem ou rede) e `CrashLoopBackOff` (o container inicia e morre — veja `kubectl logs --previous`).

**Limitação deste nível**: se o Pod morrer, ninguém o recria.

## Nível 2: Deployment

O Deployment mantém o número desejado de réplicas, recria Pods que falham e faz atualizações graduais (*rolling updates*) com histórico para rollback<Cite id="k8s-deployment" />.

<Figure src="/images/k8s/deployment.png" alt="Deployment gerenciando um ReplicaSet com três Pods" />

```yaml title="deployment.yaml"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx            # deve casar com template.metadata.labels
  strategy:
    rollingUpdate:
      maxSurge: 1           # até 1 Pod extra durante a atualização
      maxUnavailable: 0     # nunca fica abaixo das réplicas desejadas
  template:
    metadata:
      labels:
        app: nginx
    spec:
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: nginx
          image: nginxinc/nginx-unprivileged:1.28-alpine
          ports:
            - containerPort: 8080
          readinessProbe:       # só recebe tráfego quando responde
            httpGet: { path: /, port: 8080 }
            periodSeconds: 5
          livenessProbe:        # reiniciado se travar
            httpGet: { path: /, port: 8080 }
            initialDelaySeconds: 10
          resources:
            requests: { cpu: 100m, memory: 64Mi }
            limits: { memory: 128Mi }
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - name: tmp
              mountPath: /tmp   # o nginx precisa de um diretório gravável
      volumes:
        - name: tmp
          emptyDir: {}
```

Esses `securityContext` atendem ao perfil **restricted** dos Pod Security Standards<Cite id="k8s-pss" />: sem root, sem escalonamento de privilégios, sem capacidades extras e com filesystem somente leitura.

```bash
kubectl apply -f deployment.yaml
kubectl get deploy,rs,pods -l app=nginx
kubectl delete pod <um-dos-pods>                # o ReplicaSet recria na hora
kubectl get pods -l app=nginx --watch
kubectl scale deployment nginx-deployment --replicas=5

# Rolling update e rollback
kubectl set image deployment/nginx-deployment nginx=nginxinc/nginx-unprivileged:1.29-alpine
kubectl rollout status deployment/nginx-deployment
kubectl rollout history deployment/nginx-deployment
kubectl rollout undo deployment/nginx-deployment
```

## Nível 3: Service

O Service cria um IP virtual estável (ClusterIP) e um nome DNS (`nginx-service.default.svc.cluster.local`), encaminhando o tráfego para os Pods **prontos** que casam com o seletor<Cite id="k8s-service" />.

<Figure src="/images/k8s/service.png" alt="Service balanceando tráfego entre três Pods" />

```yaml title="service.yaml"
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  type: NodePort        # ClusterIP (padrão) | NodePort | LoadBalancer | ExternalName
  selector:
    app: nginx
  ports:
    - protocol: TCP
      port: 80          # porta do Service
      targetPort: 8080  # porta do container
      nodePort: 30080   # faixa padrão 30000–32767
```

```bash
kubectl apply -f service.yaml
kubectl get svc nginx-service

# Endpoints reais por trás do Service (a API Endpoints foi depreciada em favor de EndpointSlices)
kubectl get endpointslices -l kubernetes.io/service-name=nginx-service

curl -s http://localhost:30080 | grep -i "<title>"

# Distribuição das requisições entre os Pods
for i in $(seq 1 10); do curl -s -o /dev/null http://localhost:30080; done
kubectl logs -l app=nginx --prefix --tail=5
```

O comando `kubectl get endpoints` ainda funciona, mas emite um aviso de depreciação: use **EndpointSlices**<Cite id="k8s-endpointslices" />. No modo padrão do kube-proxy, o backend é escolhido aleatoriamente entre os endpoints prontos — o mesmo comportamento do simulador acima.

**Limitações**: portas altas (30000–32767), uma porta por aplicação e nenhum roteamento por domínio.

## Nível 4: Ingress e Gateway API

O Ingress expõe vários Services nas portas 80/443 com roteamento por **host** e **caminho**, além de TLS centralizado<Cite id="k8s-ingress" />.

<Figure src="/images/k8s/ingress.png" alt="Ingress roteando tráfego HTTP para Services" />

<Callout type="warning" title="O ecossistema mudou: Ingress congelado, Ingress NGINX aposentado">
A API Ingress continua disponível, mas está **congelada** — novos recursos vão para o **Gateway API**<Cite id="gateway-api" />. Além disso, o projeto comunitário **Ingress NGINX** foi aposentado: a manutenção terminou em março de 2026, sem novas versões nem correções de segurança<Cite id="ingress-nginx-retirement" />. Para novos projetos, prefira o Gateway API.
</Callout>

O k3s já vem com o **Traefik** como controlador<Cite id="k3s-networking" />. Primeiro, volte o Service para `ClusterIP` (o tráfego externo passará pelo Traefik):

```yaml title="service.yaml (ajustado)"
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  type: ClusterIP
  selector:
    app: nginx
  ports:
    - port: 80
      targetPort: 8080
```

<Tabs labels={["Ingress (clássico)", "Gateway API (recomendado)"]}>
<Tab>

```yaml title="ingress.yaml"
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nginx-ingress
spec:
  ingressClassName: traefik
  rules:
    - host: nginx.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: nginx-service
                port:
                  number: 80
```

</Tab>
<Tab>

```yaml title="httproute.yaml"
# Requer os CRDs do Gateway API e um controlador habilitado
# (no k3s, o provedor kubernetesGateway do Traefik). Veja a documentação oficial.
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: nginx-route
spec:
  parentRefs:
    - name: traefik-gateway      # Gateway criado pelo controlador
      namespace: kube-system
  hostnames: ["nginx.local"]
  rules:
    - matches:
        - path: { type: PathPrefix, value: / }
      backendRefs:
        - name: nginx-service
          port: 80
```

</Tab>
</Tabs>

```bash
kubectl get pods -n kube-system -l app.kubernetes.io/name=traefik
kubectl apply -f service.yaml -f ingress.yaml
kubectl get ingress
curl -H "Host: nginx.local" http://localhost      # simula o domínio
sudo ss -tulpn | grep ':80 '                       # quem escuta na 80 do host
kubectl logs -n kube-system -l app.kubernetes.io/name=traefik --tail=20
```

## Nível 5: ConfigMap e Secret

- **ConfigMap**: configuração não sensível (variáveis, arquivos inteiros)<Cite id="k8s-configmap" />.
- **Secret**: dados sensíveis. Os valores ficam em **base64 — codificação, não criptografia**.

```yaml title="configmap.yaml"
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-config
data:
  APP_NAME: "Meu Nginx"
  APP_VERSION: "1.0.0"
  default.conf: |
    server {
        listen 8080;
        location / {
            root /usr/share/nginx/html;
            index index.html;
        }
        add_header X-Config-From "ConfigMap" always;
    }
  index.html: |
    <!doctype html>
    <html lang="pt-BR">
      <head><meta charset="utf-8"><title>Nginx com ConfigMap</title></head>
      <body><h1>Página servida a partir de um ConfigMap 🚀</h1></body>
    </html>
```

```yaml title="secret.yaml"
apiVersion: v1
kind: Secret
metadata:
  name: nginx-secret
type: Opaque
stringData:                 # o Kubernetes converte para base64
  DB_USERNAME: "app"
  DB_PASSWORD: "troque-por-um-segredo-real"
```

<Callout type="security" title="Secrets de verdade">
Não versione `secret.yaml` com valores reais. Habilite **criptografia em repouso** no etcd, restrinja `get/list` de Secrets via RBAC e use ferramentas como External Secrets Operator, Sealed Secrets ou SOPS<Cite id="k8s-secrets-good-practices" />. Prefira montar segredos como **arquivos** em vez de variáveis de ambiente, que vazam com mais facilidade (logs, *crash dumps*, processos filhos).
</Callout>

```yaml title="deployment-com-config.yaml (trecho de spec.template.spec)"
containers:
  - name: nginx
    image: nginxinc/nginx-unprivileged:1.28-alpine
    envFrom:
      - configMapRef:
          name: nginx-config
    volumeMounts:
      - name: config
        mountPath: /etc/nginx/conf.d       # diretório inteiro: recebe atualizações
      - name: html
        mountPath: /usr/share/nginx/html
      - name: db-credentials
        mountPath: /var/run/secrets/db     # segredos como arquivos
        readOnly: true
volumes:
  - name: config
    configMap:
      name: nginx-config
      items: [{ key: default.conf, path: default.conf }]
  - name: html
    configMap:
      name: nginx-config
      items: [{ key: index.html, path: index.html }]
  - name: db-credentials
    secret:
      secretName: nginx-secret
```

```bash
kubectl apply -f configmap.yaml -f secret.yaml
kubectl describe secret nginx-secret            # mostra as chaves, não os valores
kubectl get secret nginx-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d   # base64 ≠ criptografia!

# Mudou o ConfigMap? Variáveis de ambiente só mudam com novos Pods:
kubectl rollout restart deployment nginx-deployment-config
```

<Callout type="info" title="Atualização automática de ConfigMaps">
Volumes de ConfigMap montados como **diretório** são atualizados pelo kubelet após alguns segundos/minutos. Já montagens com **`subPath`** (usadas na versão anterior deste artigo) **nunca** recebem atualizações, e variáveis de ambiente só mudam quando o Pod é recriado<Cite id="k8s-configmap" />.
</Callout>
