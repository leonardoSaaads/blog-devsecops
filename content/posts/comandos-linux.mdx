## A jornada de quem não sabe por onde começar

Quando comecei a me aprofundar em Linux, eu me sentia completamente perdido. O terminal era aquela tela preta intimidadora, cheia de comandos que pareciam escritos em outra língua. Eu não entendia o que eram distribuições, por que existiam tantas, nem por que todo mundo na área de tecnologia falava sobre isso com tanto entusiasmo — ou terror.

Com o tempo, padrões começaram a fazer sentido. No trabalho você acaba precisando de um `| grep erro` ou de um `tail -f` em um log de produção; vai resolvendo problemas e, de repente, está lidando com servidores, containers e pipelines de CI/CD.

Mas aqui está a verdade que ninguém conta: **executar comandos não é entender Linux**. A diferença entre decorar `ls -la` e compreender o modelo de arquivos e processos do Unix fica brutal quando você está depurando um container quebrado às 1h39 da manhã<Cite id="kerrisk-tlpi" />.

Este guia é o que eu gostaria de ter recebido quando comecei: menos lista de comandos, mais **por que** as coisas funcionam como funcionam.

## Distribuições não são apenas sabores diferentes

### O que são distribuições, afinal?

**Linux é só o kernel**: o núcleo que conversa com o hardware. Sozinho, ele não entrega um sistema utilizável — faltam shell, bibliotecas, gerenciador de pacotes e serviços. Uma **distribuição** empacota o kernel com esse conjunto de software, configurações padrão e uma filosofia de manutenção.

| Distribuição | Base | Público-alvo | Filosofia |
| --- | --- | --- | --- |
| Debian | Independente | Servidores, estabilidade | Software livre, ciclos de teste longos |
| Ubuntu | Debian | Desktop e servidores | Facilidade + suporte comercial (LTS) |
| Fedora / RHEL | Independente | Corporativo, inovação | RHEL estável; Fedora como vitrine |
| Arch | Independente | Usuários avançados | Rolling release, controle total |
| Mint | Ubuntu | Iniciantes | Desktop amigável |
| Pop!_OS | Ubuntu | Desenvolvedores | Drivers e fluxo de trabalho otimizados |
| Alpine | Independente | Containers | Mínima: musl + BusyBox |

### Por que isso importa no mundo real?

Ao escolher a base de uma imagem de container, a decisão afeta:

- **Tamanho**: a imagem `alpine` tem poucos MB compactada; a `ubuntu` tem algumas dezenas de MB.
- **Superfície de ataque**: menos pacotes, menos CVEs para corrigir<Cite id="docker-best-practices" />.
- **Compatibilidade**: o Alpine usa a biblioteca C **musl** em vez da **glibc**; binários pré-compilados (e algumas *wheels* Python) podem não funcionar.
- **Atualização**: `apt`, `dnf` ou `apk` — cada ecossistema tem seu ciclo de correções.

Debian e derivados (como o Ubuntu) estão entre as distribuições mais usadas em servidores web segundo levantamentos públicos<Cite id="w3techs-linux" />. Entender o ecossistema `apt`/`dpkg` não é opcional.

### Perguntas que você precisa saber responder

1. **Qual base usar para imagens mínimas?** Alpine ou imagens *distroless*/*slim* — o critério é compatibilidade + superfície de ataque, não só tamanho.
2. **Como atualizar pacotes?**

<Tabs labels={["Debian/Ubuntu", "Alpine", "Fedora/RHEL"]}>
<Tab>

```bash
sudo apt update && sudo apt upgrade
```

</Tab>
<Tab>

```bash
apk update && apk upgrade
```

</Tab>
<Tab>

```bash
sudo dnf upgrade --refresh
```

</Tab>
</Tabs>

3. **O que é `/etc/apt/sources.list.d/`?** É onde ficam as definições de repositórios. O `apt update` consulta essas fontes para descobrir pacotes e versões disponíveis — entender isso é essencial para resolver conflitos de dependências.
4. **Preciso de interface gráfica no servidor?** Não. Ela consome recursos e amplia a superfície de ataque.

### Exemplo prático: Dockerfile enxuto e seguro

```docker title="Dockerfile"
FROM python:3.14-alpine

WORKDIR /app

# Dependências de compilação (apk é o gerenciador do Alpine)
RUN apk add --no-cache gcc musl-dev linux-headers

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# Nunca rode a aplicação como root dentro do container
RUN adduser -D -u 10001 app
USER app

EXPOSE 8000
# Servidor WSGI de produção (o servidor de desenvolvimento do Flask não serve para isso)
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "app:app"]
```

<Callout type="security" title="Nunca use flask run --debug em produção">
O modo debug ativa o depurador interativo do Werkzeug, que permite **executar código arbitrário** no servidor a partir do navegador<Cite id="werkzeug-debugger" />. A versão anterior deste artigo usava `flask run --debug` no `CMD` — use um servidor WSGI (como o Gunicorn) e um usuário sem privilégios<Cite id="owasp-docker" />.
</Callout>

## Permissões não são apenas chmod 777

### O erro que todo iniciante comete

Um dos erros clássicos — que eu cometi e vejo **constantemente** — é tratar permissões como detalhe: "dá um `chmod 777` que funciona". Em DevSecOps, o modelo de permissões Unix é a **primeira linha de defesa**.

### Lendo a saída do ls -l

```text
-rw-r----- 1 root root 696969 out 24 2024 arquivo.pdf
│└┬┘└┬┘└┬┘   │    │     │      │            └ nome
│ │  │  │    │    │     │      └ data de modificação
│ │  │  │    │    │     └ tamanho em bytes
│ │  │  │    │    └ grupo dono
│ │  │  │    └ usuário dono
│ │  │  └ outros (others): sem permissões
│ │  └ grupo (group): leitura
│ └ dono (user): leitura e escrita
└ tipo: - arquivo, d diretório, l link simbólico, b/c dispositivos
```

Cada trio é formado por **r** (leitura = 4), **w** (escrita = 2) e **x** (execução = 1). Somando os valores de cada trio obtemos a forma octal: `rwx` = 7, `r-x` = 5, `r--` = 4. Assim, `chmod 750 arquivo` significa dono `rwx`, grupo `r-x` e outros sem acesso<Cite id="man-chmod" />.

Experimente abaixo: marque as caixas, digite um modo octal ou use os atalhos. Observe os alertas de segurança.

### Princípios fundamentais de segurança

**1. Menor privilégio.** Cada usuário ou processo recebe exatamente o que precisa — nem mais, nem menos.

```bash
# Errado: qualquer conta local pode alterar o site
chmod -R 777 /var/www/html

# Correto: dono gerencia; o servidor web (grupo) só lê
chown -R deploy:www-data /var/www/html
find /var/www/html -type d -exec chmod 750 {} +
find /var/www/html -type f -exec chmod 640 {} +
```

**2. Segregação de responsabilidades.** Quem executa não precisa modificar:

```bash
chown deploy:developers deploy.sh
chmod 750 deploy.sh   # o grupo executa, mas não altera
```

**3. Evite o 777 como se fosse a peste.** Ele permite que *qualquer* conta comprometida altere o arquivo. Um cenário real:

1. Um atacante obtém acesso SSH com um usuário comum.
2. Encontra `deploy.sh` com permissão 777 e injeta um minerador de criptomoedas.
3. No próximo deploy automático — executado com privilégios — o código malicioso roda.

### Comandos essenciais

```bash
ls -l arquivo.txt                  # ver permissões
chmod 640 arquivo.txt              # forma numérica
chmod u=rw,g=r,o= arquivo.txt      # forma simbólica
chown usuario:grupo arquivo.txt    # dono e grupo
chgrp developers arquivo.txt       # apenas o grupo
umask                              # máscara atual

# Auditoria: arquivos com escrita para "outros" (world-writable)
find / -xdev -type f -perm -o+w 2>/dev/null
```

### umask: a configuração que ninguém explica direito

A `umask` define quais bits **não** serão concedidos a arquivos e diretórios recém-criados. Arquivos partem de `666` e diretórios de `777`; o resultado é calculado com uma operação bit a bit — **E lógico com o complemento da máscara** — e não por subtração<Cite id="man-umask" />:

$$
\text{permissão} = \text{base} \;\land\; \lnot\,\text{umask}
$$

Com `umask 022`, ambos os métodos coincidem (`666 → 644`, `777 → 755`), o que esconde o detalhe. Com `umask 033`, a subtração daria `633`, mas o resultado real é `644`: o bit de execução que a máscara removeria nem existia na base. Teste valores diferentes no laboratório acima.

```bash
umask 077   # arquivos 600, diretórios 700: tudo privado por padrão
```

## Comandos que eu gostaria que tivessem me ensinado

### find — auditoria e troubleshooting

```bash
find /var/log/nginx -name "*.log"                 # por nome
find /var/www -type f -perm -o+w                  # world-writable (auditoria)
find /etc -type f -mtime -1                       # alterados nas últimas 24 h
find /var -xdev -type f -size +100M               # arquivos grandes
find /home -user joao -type f                     # por dono
find /tmp -type f -name "*.tmp" -mtime +7 -delete # limpeza
find /var/www -type f -name "*.php" -exec chmod 640 {} +
```

**Cenário real**, disco cheio às 2h da manhã:

```bash
du -xh / 2>/dev/null | sort -rh | head -20   # onde está o espaço?
docker system df                              # quanto o Docker ocupa?
```

### grep — análise de logs

```bash
grep -i "error" /var/log/syslog           # sem diferenciar maiúsculas
grep -C 5 "Exception" /var/log/app.log    # 5 linhas de contexto
grep -c " 404 " /var/log/nginx/access.log # contar ocorrências
grep -v "DEBUG" /var/log/app.log          # inverter o filtro
grep -E "error|fail|critical" /var/log/syslog
```

Um pipeline de análise — repare que **comentários não podem vir depois da barra invertida** de continuação de linha (um erro presente na versão anterior deste artigo):

```bash
# Filtra erros, remove ruído conhecido, extrai data e mensagem e ranqueia
grep -i "error" /var/log/app.log \
  | grep -v "DeprecationWarning" \
  | awk '{print $1, $2, $NF}' \
  | sort | uniq -c | sort -rn | head -20
```

### tail e journalctl — acompanhamento em tempo real

```bash
tail -n 50 arquivo.log
tail -f /var/log/syslog          # acompanha
tail -F /var/log/app.log         # acompanha mesmo se o arquivo for recriado
journalctl -u nginx -f           # serviços gerenciados pelo systemd
journalctl -p err --since "1 hour ago"
```

### ps, top e htop — processos

```bash
ps aux --sort=-%cpu | head -20   # maiores consumidores de CPU
ps aux --sort=-%mem | head -20   # maiores consumidores de memória
ps -ef --forest                  # árvore pai → filho
```

Colunas importantes: `PID`, `%CPU`, `%MEM`, `RSS` (memória física real) e `STAT` (S = dormindo, R = executando, Z = zumbi, D = espera ininterrompível, geralmente I/O).

### ss — conexões de rede

```bash
ss -tuln          # portas TCP/UDP em escuta
sudo ss -tulnp    # ...com o processo dono (requer root)
ss -tn state established '( dport = :5432 )'
```

**Cenário real**: a aplicação não conecta ao banco.

```bash
sudo ss -tulnp | grep 5432          # o PostgreSQL está escutando?
nc -zv localhost 5432               # a porta responde? (substitui o telnet)
sudo nft list ruleset               # regras de firewall (nftables)
```

## Processos e sinais

**Sinais** são notificações assíncronas que o kernel ou outros processos enviam a um processo<Cite id="man-signal" />.

- **SIGTERM (15)** — pedido educado de encerramento. O processo pode salvar estado e fechar conexões. **Use sempre primeiro.**
- **SIGKILL (9)** — encerramento imediato pelo kernel; não pode ser capturado nem ignorado. Dados em memória são perdidos.
- **SIGHUP (1)** — originalmente "terminal desconectado"; hoje muitos daemons (nginx, por exemplo) o usam para **recarregar configuração**.
- **SIGSTOP / SIGCONT (19 / 18 em x86)** — pausa e retomada; o SIGSTOP também não pode ser capturado.

```bash
kill -l              # lista os sinais
kill 1234            # SIGTERM (padrão)
kill -HUP 1234       # recarregar configuração
kill -9 1234         # último recurso
```

### Containers e sinais

O `docker stop` envia SIGTERM ao processo principal (PID 1), aguarda o período de tolerância (10 s por padrão) e então envia SIGKILL<Cite id="docker-stop" />. No Kubernetes o comportamento é análogo, controlado por `terminationGracePeriodSeconds`<Cite id="k8s-pod-termination" />.

<Callout type="warning" title="A armadilha do PID 1">
Dentro de um container, o processo PID 1 **não recebe os tratadores padrão de sinais** do kernel: se a aplicação não tratar SIGTERM explicitamente, ela simplesmente ignora o sinal e só morre no SIGKILL. Use a forma *exec* do `CMD` (lista JSON, sem shell intermediário) e, se necessário, um init mínimo como `docker run --init`.
</Callout>

Aplicação que trata o sinal corretamente:

```python title="app.py"
import signal
import sys
import time

def encerrar(sig, frame):
    print("Encerrando graciosamente…")
    # salvar estado, fechar conexões etc.
    sys.exit(0)

signal.signal(signal.SIGTERM, encerrar)
signal.signal(signal.SIGINT, encerrar)

while True:
    print("Processando…")
    time.sleep(1)
```

No Kubernetes, combine o tratamento do sinal com um `preStop` para drenar conexões:

```yaml
spec:
  terminationGracePeriodSeconds: 30
  containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 10"]
```

## Filesystem: tudo é arquivo

No Unix, dispositivos, processos e até informações do kernel são expostos como arquivos. É essa abstração que permite depurar sem ferramentas mágicas: quer saber o que um processo está fazendo? Leia `/proc/PID/`<Cite id="man-proc" />.

### Não existe C: ou D:

Existe **uma única árvore**, a partir de `/`, organizada pelo *Filesystem Hierarchy Standard*<Cite id="fhs" />:

```text
/
├── bin, sbin → hoje links para /usr/bin e /usr/sbin na maioria das distros
├── boot       kernel e bootloader
├── dev        dispositivos
├── etc        configuração do sistema
├── home       diretórios dos usuários
├── opt        software opcional de terceiros
├── proc, sys  pseudo-sistemas de arquivos do kernel (não ocupam disco)
├── run        dados de execução (PIDs, sockets)
├── tmp        temporários (sticky bit: cada um apaga só o que é seu)
├── usr        programas e bibliotecas
└── var        dados variáveis: logs, cache, filas
```

### /proc: janela para o kernel

```bash
cat /proc/cpuinfo /proc/meminfo /proc/uptime
PID=$$                                   # o próprio shell
ls -l /proc/$PID/cwd /proc/$PID/exe      # diretório e executável
ls -l /proc/$PID/fd/                     # descritores abertos
tr '\0' '\n' < /proc/$PID/environ        # variáveis de ambiente
grep -E 'VmRSS|Threads' /proc/$PID/status
```

### /dev: dispositivos como arquivos

```bash
comando 2>/dev/null                          # descartar erros
dd if=/dev/zero of=teste.bin bs=1M count=100 # arquivo de 100 MB
head -c 32 /dev/urandom | base64             # segredo aleatório
clear                                        # limpar o terminal
```

<Callout type="info" title="/dev/random × /dev/urandom">
A ideia de que `/dev/urandom` seria "menos aleatório" é um mito antigo. Nos kernels modernos (5.6+), ambos são servidos pelo mesmo CSPRNG; `/dev/random` só bloqueia antes de o gerador ser inicializado no boot<Cite id="man-random" />. Para gerar chaves e tokens, `/dev/urandom` (ou `getrandom(2)`) é a escolha correta.
</Callout>

## Pipes e redirecionamento: o superpoder Unix

A filosofia Unix, resumida por Doug McIlroy<Cite id="salus-unix" />:

> Escreva programas que façam uma coisa e a façam bem. Escreva programas que trabalhem juntos. Escreva programas que lidem com fluxos de texto, pois essa é uma interface universal.

```bash
echo "teste" > arquivo.txt        # sobrescreve
echo "mais" >> arquivo.txt        # acrescenta
sort < lista.txt                  # entrada a partir de arquivo
comando 2> erros.log              # apenas stderr
comando > tudo.log 2>&1           # stdout + stderr
comando &> tudo.log               # equivalente (bash)
```

Top 10 IPs que mais fizeram POST no nginx:

```bash
grep '"POST' /var/log/nginx/access.log \
  | awk '{print $1}' \
  | sort | uniq -c | sort -rn | head -10
```

## O que realmente importa

1. **Tudo tem contexto de segurança**: quem é o dono, quem acessa e o que pode ser feito.
2. **Logs são eventos estruturados**: data, severidade e contexto — saber extraí-los é crítico.
3. **O sistema é composável**: pipes e redirecionamentos resolvem a maior parte do dia a dia.
4. **Imutabilidade é segurança**: containers *read-only*, configuração versionada (GitOps), SELinux/AppArmor.
5. **Pense em camadas**: aplicação → runtime → userspace → kernel → hardware. Saber onde investigar economiza horas.

## Conclusão

A diferença entre júnior e sênior não está em quantos comandos alguém decorou, mas em entender **por que** as coisas funcionam, saber **onde** procurar quando algo quebra e conhecer a arquitetura por baixo dos panos. Linux não é difícil — é **diferente**. Suba uma VM, quebre coisas propositalmente e conserte. É assim que se aprende.
