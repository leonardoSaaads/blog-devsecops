## 1. Por que as linguagens têm velocidades diferentes?

Se todas rodam no mesmo hardware, por que algumas são mais rápidas? Pense em línguas humanas. Em português:

```text
Eu gosto de comer arroz de noite.
```

Em mandarim:

```text
我 喜欢 晚上 吃 米饭。(Wǒ xǐhuān wǎnshàng chī mǐfàn.)
```

O mandarim é mais **denso**: cada caractere representa um morfema ou palavra. O preço é uma barreira de entrada maior — milhares de caracteres e muita dependência de contexto. O português prioriza clareza estrutural em detrimento da economia de símbolos.

Linguagens de programação enfrentam trade-offs parecidos: **densidade × curva de aprendizado**, **compilada × interpretada**, **controle × abstração**.

## 2. Uma breve história: do Assembly aos LLMs

### Assembly: conversando com o processador

```asm
MOV AX, 01      ; carrega 1
ADD AX, 02      ; soma 2
MOV [1000], AX  ; guarda o resultado na memória
```

Trabalhoso? Muito. Rápido? Extremamente: você controla cada ciclo e cada byte.

### C: o "Assembly portátil"

Em 1972, Dennis Ritchie criou o C nos Bell Labs, junto ao desenvolvimento do Unix: algo mais legível que ainda compilasse para código de máquina eficiente<Cite id="ritchie-1993" />.

```c
int resultado = 1 + 2;
```

### A era da abstração: Python, Ruby, JavaScript

Com computadores mais potentes, surgiu a pergunta: por que se preocupar com memória e tipos? Compare:

```c
char *nome = malloc(50);
strcpy(nome, "João");
/* … usa a variável … */
free(nome); /* esqueceu? vazamento. Liberou duas vezes? vulnerabilidade. */
```

```python
nome = "João"  # pronto
```

O Python é um mordomo: cuida dos detalhes — e cobra em desempenho.

### A síntese moderna: Go, Rust, Swift

- **Go**: compilação rápida, concorrência simples e binários estáticos.
- **Rust**: desempenho de C **com** segurança de memória verificada em tempo de compilação<Cite id="blandy-2021" />.
- **Swift**: segurança e ergonomia no ecossistema Apple.

E hoje os assistentes baseados em LLMs escrevem boa parte do código *boilerplate* — o que torna ainda mais importante entender os trade-offs por trás do que é gerado.

## 3. Compiladas × interpretadas: o Uber e o carro próprio

**Compilada (C, Rust, Go)** — carro próprio: investimento inicial (compilação), rota planejada (otimizações), execução direta.

**Interpretada (Python, Ruby)** — Uber: sem manutenção (coletor de lixo), pede e sai (sem compilação), mas pode pegar trânsito (overhead do interpretador).

### O que acontece em resultado = 5 + 3

```text
C (compilado)                          CPython (bytecode interpretado)
1. compilado antes da execução         1. compila para bytecode e interpreta
2. vira poucas instruções de máquina   2. verifica tipos dos objetos em tempo de execução
3. executa direto na CPU               3. despacha para a função de soma do tipo int
                                       4. aloca o objeto do resultado e ajusta contagens
ordem de grandeza: ~1 ns               ordem de grandeza: dezenas de ns
```

Os números são ordens de grandeza: em loops de milhões de iterações, a diferença vira milissegundos contra segundos<Cite id="vanderplas-2014" />.

### E o Java (e o JavaScript)?

A JVM compila para *bytecode* e usa um **JIT** (*Just-In-Time*): observa os trechos mais executados e os compila para código de máquina em tempo de execução. Os motores JavaScript (como o V8) fazem o mesmo — por isso o JavaScript moderno costuma ser bem mais rápido que o Python puro em laços numéricos.

<Callout type="info" title="O Python também está mudando">
O CPython 3.13 trouxe um JIT experimental<Cite id="pep-744" /> e uma build opcional **sem GIL** (*free-threaded*)<Cite id="pep-703" />; no Python 3.14, essa build passou a ser oficialmente suportada<Cite id="pep-779" />, permitindo paralelismo real com threads em CPU.
</Callout>

## 4. A medição das linguagens faz sentido?

### O Benchmarks Game: a corrida em pista fechada

Aquele gráfico "C é 100× mais rápido que Python" costuma vir do Computer Language Benchmarks Game<Cite id="benchmarks-game" />, que mede algoritmos numéricos e manipulação de strings — e de estudos que mostram como energia, tempo e memória se relacionam<Cite id="pereira-2017,pereira-2021" />. É como comparar carros apenas em arrancada: a Ferrari vence, mas tente fazer baliza com ela.

### O que esses benchmarks não medem

1. **Tempo de desenvolvimento**:

```python
import requests

usuarios = requests.get("https://api.exemplo.com/users", timeout=10).json()
print([u["name"] for u in usuarios if u["age"] > 18])
```

Em C, o mesmo exige cliente HTTP, parser de JSON e gerenciamento manual de memória.

2. **Manutenibilidade**: código legível é código que você entende seis meses depois.
3. **Ecossistema**: o PyPI reúne centenas de milhares de projetos.
4. **Segurança de memória**: C é rápido — até um *buffer overflow* virar uma CVE crítica.

### Meça você mesmo: algoritmo × linguagem

Execute os dois blocos abaixo. Primeiro em JavaScript (motor V8/SpiderMonkey com JIT); depois o mesmo em Python, rodando no seu navegador via **Pyodide** (CPython compilado para WebAssembly — mais lento que o CPython nativo, então compare apenas **proporções**).

```javascript runnable title="Fibonacci: recursão ingênua × iteração (JavaScript)"
function fibRecursivo(n) {
  return n < 2 ? n : fibRecursivo(n - 1) + fibRecursivo(n - 2);
}

function fibIterativo(n) {
  let [a, b] = [0n, 1n];
  for (let i = 0; i < n; i++) [a, b] = [b, a + b];
  return a;
}

console.time("recursivo fib(30)");
console.log(fibRecursivo(30));
console.timeEnd("recursivo fib(30)");

console.time("iterativo fib(30)");
console.log(fibIterativo(30));
console.timeEnd("iterativo fib(30)");

console.time("iterativo fib(1000)");
console.log(String(fibIterativo(1000)).slice(0, 20) + "…");
console.timeEnd("iterativo fib(1000)");
```

```python runnable title="O mesmo experimento em Python (Pyodide)"
import time
from functools import lru_cache

def fib_recursivo(n):
    return n if n < 2 else fib_recursivo(n - 1) + fib_recursivo(n - 2)

@lru_cache(maxsize=None)
def fib_memo(n):
    return n if n < 2 else fib_memo(n - 1) + fib_memo(n - 2)

def medir(rotulo, func, n):
    inicio = time.perf_counter()
    resultado = func(n)
    print(f"{rotulo:>16}: fib({n}) = {resultado}  em {(time.perf_counter() - inicio) * 1000:.2f} ms")

medir("recursivo", fib_recursivo, 25)
medir("memoizado", fib_memo, 25)
medir("memoizado", fib_memo, 300)
```

Repare: trocar o **algoritmo** (exponencial → linear) muda o tempo em ordens de grandeza, muito mais do que trocar de linguagem. É exatamente o ponto deste artigo.

### A falácia da otimização prematura

Donald Knuth escreveu: *"devemos esquecer as pequenas eficiências, digamos em 97% do tempo: a otimização prematura é a raiz de todo mal"* — e completou que não devemos desperdiçar as oportunidades nos 3% críticos<Cite id="knuth-1974" page="268" />. A estratégia pragmática<Cite id="pragmatic-2019" />:

```text
1. Atende ao requisito com a linguagem que o time domina?  → siga em frente.
2. Ficou lento?                                            → meça com um profiler; não adivinhe.
3. O gargalo é algoritmo/I/O?                              → corrija o algoritmo (Big-O), cache, índices.
4. Ainda é CPU-bound depois disso?                         → reescreva só o trecho crítico em C/Rust.
```

### Prepare o ambiente, não a linguagem

Infraestrutura costuma pesar mais que a linguagem: cache (Redis), balanceamento de carga, CDN e índices no banco. Um exemplo clássico com o ORM do Django:

```python
# "Lento": N+1 consultas (uma por usuário)
for user in User.objects.all():
    print(user.address.city)

# "Rápido": um JOIN — mesma linguagem
for user in User.objects.select_related("address"):
    print(user.address.city)
```

## 5. O futuro é poliglota: FFI

O futuro não é escolher **uma** linguagem — é **combinar** várias. Uma orquestra só de violinos é possível, mas por quê?

**FFI (*Foreign Function Interface*)** é a capacidade de uma linguagem chamar código de outra.

### Python chamando C com ctypes

```c title="calculo_pesado.c"
long long fibonacci(int n) {
    long long a = 0, b = 1;
    for (int i = 0; i < n; i++) {
        long long t = a + b;
        a = b;
        b = t;
    }
    return a;
}
```

```bash
gcc -O2 -shared -fPIC -o calculo_pesado.so calculo_pesado.c
```

```python title="usa_c.py"
import ctypes

lib = ctypes.CDLL("./calculo_pesado.so")
lib.fibonacci.argtypes = [ctypes.c_int]
lib.fibonacci.restype = ctypes.c_longlong

print(lib.fibonacci(50))  # velocidade de C, ergonomia de Python
```

Declarar `argtypes` e `restype` não é opcional: sem isso, o `ctypes` assume `int` e o resultado pode ser truncado ou corrompido<Cite id="python-ctypes" />.

### Python chamando Rust com PyO3

```rust title="src/lib.rs"
use pyo3::prelude::*;

#[pyfunction]
fn soma(dados: Vec<i64>) -> i64 {
    dados.iter().sum()
}

#[pymodule]
fn minha_lib(m: &Bound<'_, PyModule>) -> PyResult<()> {
    m.add_function(wrap_pyfunction!(soma, m)?)?;
    Ok(())
}
```

```bash
pip install maturin && maturin develop --release
python -c "import minha_lib; print(minha_lib.soma([1, 2, 3]))"
```

A API `Bound<'_, PyModule>` substituiu a antiga `&PyModule` (usada na versão anterior deste artigo) a partir do PyO3 0.21<Cite id="pyo3" />.

### Ecossistemas híbridos que você já usa

- **NumPy**: você escreve Python; as operações vetoriais rodam em C otimizado.
- **Node.js**: `createHash` do módulo `node:crypto` executa C/C++ (OpenSSL) por baixo.

```javascript
import { createHash } from "node:crypto";
console.log(createHash("sha256").update("dados").digest("hex"));
```

### WebAssembly: o FFI do navegador

O WebAssembly é um formato binário portátil e seguro que roda em velocidade próxima da nativa no navegador<Cite id="haas-2017,mdn-wasm" />. Rust, C/C++ e Go compilam para ele. É, aliás, como o Python do playground acima roda na sua máquina.

```rust
use wasm_bindgen::prelude::*;

#[wasm_bindgen]
pub fn inverter_pixels(dados: &[u8]) -> Vec<u8> {
    dados.iter().map(|p| 255 - p).collect()
}
```

Aplicações reais: Figma, AutoCAD Web e Google Earth executam C++ no navegador via WebAssembly.

### Ferramentas de FFI

| Origem | Alvo | Ferramenta |
| --- | --- | --- |
| Python | C/C++ | ctypes, cffi, Cython |
| Python | Rust | PyO3 + maturin |
| JavaScript (Node) | C/C++ | Node-API (node-addon-api) |
| JavaScript (Node) | Rust | napi-rs, Neon |
| Go | C | cgo<Cite id="cgo" /> |
| Qualquer | WebAssembly | Emscripten, wasm-bindgen |

### Casos reais de migração

- O **Discord** migrou um serviço crítico de Go para Rust para eliminar picos de latência causados pelo coletor de lixo<Cite id="discord-rust" />.
- O **Dropbox** reescreveu o núcleo do motor de sincronização em Rust<Cite id="dropbox-sync" />.

Note o padrão: reescreveram **partes críticas**, medidas e justificadas — não o sistema inteiro por moda.

## 6. Conclusão: velocidade importa, mas não do jeito que você pensa

Em ordem de prioridade:

1. **Resolver o problema** — código que não existe não roda rápido.
2. **Manutenibilidade** — código que ninguém entende vira legado.
3. **Produtividade** — tempo é dinheiro.
4. **Ecossistema** — não reinvente a roda.
5. **Desempenho** — quando medido e necessário<Cite id="gorelick-2020" />.

A mentalidade vencedora: **MVP** na linguagem que você domina → **perfilamento** para achar gargalos reais → **hibridização** apenas do que é crítico.
